Library

Tsuji

Languages, typed message families, per-language catalogues, ICU MessageFormat 2.0 and locale-aware number and date formatting, for Scala 3 on the JVM and Scala.js.

The tsuji (通詞) were the official interpreters of Nagasaki in the Edo period. Up to 4.x the library was called taihei-i18n.

5.0.0 on Maven Central

Install

Scala 3.9 or later. On the JVM:

// Mill
mvn"dev.taihei::taihei-tsuji:5.0.0"

// sbt
libraryDependencies += "dev.taihei" %% "taihei-tsuji" % "5.0.0"

On Scala.js, the same artifact with :: in Mill and %%% in sbt.

The JVM-only taihei-tsuji-tools is a program that exports catalogue files for translators and browsers:

// Mill
mvn"dev.taihei::taihei-tsuji-tools:5.0.0"

// sbt
libraryDependencies += "dev.taihei" %% "taihei-tsuji-tools" % "5.0.0"

Quick start

A message family groups messages under a key prefix. Its arguments are named and typed, and the compiler checks the templates:

import java.time.LocalDate
import dev.taihei.tsuji.*
import dev.taihei.tsuji.Language.*

object Orders extends MessageFamily("order"):
  val cancelled = message("Your order was cancelled", Dutch -> "Uw bestelling werd geannuleerd")
  val shipped   = message[(count: Int, on: LocalDate)](
    ".match {$count :plural} when one {One item shipped on {$on :date dateStyle=long}} " +
      "when * {{$count} items shipped on {$on :date dateStyle=long}}",
    Dutch -> (".match {$count :plural} when one {Eén artikel verzonden op {$on :date dateStyle=long}} " +
      "when * {{$count} artikels verzonden op {$on :date dateStyle=long}}"),
  )

given Catalogues = Catalogues(Seq(Orders))

val shipped = Orders.shipped(count = 3, on = LocalDate.of(2026, 10, 23))
shipped.localize(English)          // 3 items shipped on October 23, 2026
shipped.localize(Dutch)            // 3 artikels verzonden op 23 oktober 2026
shipped.localize(Language("de"))   // 3 items shipped on 23. Oktober 2026

A Language is a BCP 47 tag. English, Dutch and French are built in; any other is Language("de") or Language("nl-BE"). Numbers, dates and plurals are formatted for the reader's language, also when the template comes from a fallback: through java.text and java.time on the JVM, and through the browser's Intl API on Scala.js.

Translations

Translations come from two places, and both are checked the same way:

  • Inline, as trailing Language -> template pairs of message. They suit a JVM application, a library's own few languages, and tests. Inline translations are code, so in Scala.js they end up in the bundle.
  • Catalogue files, one JSON file per language, written by translators or exported with taihei-tsuji-tools. A browser application with many languages keeps its translations in files.

To show a message in a language, the registry uses the first of these that has the key: the language itself (zh-Hant-TW), the language without its extensions and private use, then with its last subtag removed step by step (zh-Hant, then zh), the fallbacks you configured for it, and finally the family's source language, which always has the key. Showing a message never throws.

On the JVM, ship catalogues as classpath resources named META-INF/taihei-tsuji/<family prefix>/<language tag>.json. They are read the first time a language is needed, with nothing to configure. In Scala.js, the application serves the exported files and loads a language with CatalogueLoader.load(catalogues, language, url). Until it arrives, messages show through the fallback chain.

Coming from taihei-i18n 4.x

Taihei Tsuji 5.0.0 is the successor of dev.taihei::taihei-i18n 4.x under a new name, and the coordinates and the package change with it:

  • the dependency is dev.taihei::taihei-tsuji, where it was dev.taihei::taihei-i18n;
  • the package is dev.taihei.tsuji, where it was dev.taihei.i18n;
  • a library ships its catalogue files under META-INF/taihei-tsuji/.

The JSON of a message and the keys of CoreMessages do not change, so a 4.x peer and a 5.x peer still exchange messages. There is no taihei-i18n 5.0.0 and no relocation: the two lines are different artifacts in different packages and can share a classpath, but their Language types are different types.

5.0.0 also replaces the 4.x Message, which carried every translation, with typed families. The 4.x type stays, unchanged and deprecated, as dev.taihei.tsuji.legacy.Message until 6.0.0. Start with the new coordinates and a change of imports:

import dev.taihei.tsuji.*
import dev.taihei.tsuji.legacy.Message   // an explicit import wins over the wildcard

Code that only builds and translates 4.x messages then compiles with deprecation warnings, and legacy and new messages are shown side by side. Then move the messages to families, one family at a time. Code that uses Message.of, Language.label, CoreMessages or the MF2 internals needs the changes listed in the migration section.

Coming from taihei-i18n 4.x on GitHub

The 4.x line keeps its name and receives security fixes for 12 months after the release of Taihei Tsuji 5.0.0: see taihei-i18n 4.x.

Coming from edo-i18n or genius-i18n

taihei-i18n 4.x has the API of com.edoframework::edo-i18n:3.0.0 and fish.genius::genius-i18n:2.0.0 under its new name, with the package dev.taihei.i18n where it was com.edoframework.i18n or genius.i18n. Coming from genius, it needs Scala 3.9 and brings zio-json 1.1, and the licence is Apache 2.0; releases up to 2.0.0 stay MIT.

Move to the newest taihei-i18n 4.0.x first, then to Taihei Tsuji 5.0.0 as above. Do not stay on 2.0.0, 3.0.0 or 4.0.0: parsing a long language tag can overflow the stack in them (advisory GHSA-45w8-x6c8-w4hg). Do not stay on 4.0.1 either: decoding or formatting a Message read from untrusted JSON can use unbounded memory and CPU in it and every earlier release (advisory GHSA-6h29-v54g-8337).
